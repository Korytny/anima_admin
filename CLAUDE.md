# Anima Admin — Pipeline Manager

Админка для производства видеороликов поверх Supabase: сезоны (`seasons`), контент-план (`topics`), сценарий, сцены (`scenes`), раскадровка, персонажи (`characters`), агенты (`agents`); настройки — пока демо.
Сейчас админка — демонстрация конвейера для продаж; цель, критерий отбора задач и текущий план — в разделе «Цель и план».
Исходное ТЗ — `README.md`. Ниже — решения, которые от него **отличаются или его уточняют**. При конфликте приоритет у этого файла.

## Команды

```bash
npm install
npm run dev        # dev-сервер Vite
npm run typecheck  # tsc --noEmit
npm run build      # typecheck + сборка
```

Окружение — `.env.local` (в git не попадает): `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` (publishable/anon).
**service_role-ключ никогда не кладём в проект и во фронтенд.**

## Стек

React 18 + TypeScript, Vite 6, Tailwind CSS v4 (`@tailwindcss/vite`, тема через `@theme` в `src/index.css`), @supabase/supabase-js, TanStack Table + Virtual, Radix (dialog, dropdown, popover, switch, slider), framer-motion, lucide-react, react-router v6, recharts, sonner, cmdk, date-fns (ru).
shadcn/ui как пакет не используется — свои компоненты в `src/components/ui.tsx`.

## База данных (Supabase)

- `public.topics` — ролики. PK `topic_id uuid`. Поля: title (NOT NULL), status (text), extended_description (сейчас не используется), script_scenas (сценарий серии от сценариста), script_shots (шоты от Редактора), music, chars text[], duration, backlog, visual_style, url, url_final, size, file_tiktok(+_size), all/all_eng jsonb, updated_at. **Нет created_at.**
- `public.seasons` — сезоны (арки из серий): title, logline, theme (сквозной вопрос), bible (markdown для агентов), source (первоисточник), status. **У каждого ролика есть сезон** — правило держит админка (выбор сезона обязателен, сезон с сериями не удаляется); в БД ограничений не ставим. Серия = topic с `season_id`; **номер серии = `topics.backlog`** (отдельной колонки нет). У серии: `logline`, `beats text[]`, `source_excerpt`. SQL: `supabase/seasons.sql`.
- `public.scenes` — сцены/шоты. PK `scene_id uuid`, `topic uuid → topics.topic_id`. Порядок: `scena` (номер сцены), затем `shot_num`. `char_img_url`, `character` — text[]; `speaker_voice_profile` — jsonb.
- `public.characters` — **библиотека персонажей сезона**. PK `id uuid`, `season uuid` (→ seasons.id; колонка переименована из `topic`, в старых записях там id ролика). Возрастные варианты — отдельные записи (`Karna_boy`, `Karna`). Серия выбирает своих в `topics.chars` (карточка серии, выбор из библиотеки). Со сценой связаны **по имени**: `scenes.character[]` / `speaking_character` ↔ `characters.name` среди персонажей сезона серии (`seasonCharacters()` + `sceneCharacters()` в store). Картинки — в одной папке сезона `anima/<seasons.folder>/characters/`. SQL: `supabase/characters_season.sql`. Файлы персонажа: `base_img`, `pers_file`, `filename` (какой главный — не определено, показываем все). `updated_at` нет.
- `public.agents` — агенты: `id bigint`, name, description, `prompt` (markdown, системный промпт), model, `is_active bool`, created_at. Ключей провайдеров в таблице нет. `{{var}}` в промпте показываются как переменные.
- Статусы — свободный text. Известные значения раскрашиваются (`lib/status.ts`), неизвестные показываются как есть серым (`statusMeta`). В topics встречаются: draft, pending, published (+ мусор).
- Доступ: Supabase Auth + RLS, разрешено только пользователям из `public.admin_users` (`supabase/policies.sql`). n8n/сервисы работают через service_role и RLS не затрагиваются.
- Остальные таблицы БД (voices, orders, stories, locations, songs, act_templates, narrative_base…) админка пока не трогает.

## Старт производства (сезоны)

Единая воронка для любого проекта; меняются только библия сезона и промпты агентов:
```
Сезон (логлайн, сквозной вопрос, библия, карта серий)
  → Серия (логлайн + 3–10 битов + выжимка первоисточника)
    → Сценарий (script_scenas) → Шоты (scenes, через Редактора) → Кадры → Видео
```
Агенты на переходах: `agents.prompt` — **системный промпт, общий, без конкретики проекта**. **Сбор данных и формирование промпта — только в n8n (бекенд), не в админке.** Админка шлёт на вебхук лишь id; n8n сам читает БД, вызывает агента и пишет результат.
- Сценарий серии: кнопка «Сгенерировать сценарий» в карточке серии → `VITE_N8N_SCRIPT_WEBHOOK`, тело `{action:'episode_script', topic_id}` (`api/pipeline.ts`). n8n пишет ответ в `topics.script_scenas`. Агент «Сценарист по битам» (`supabase/seeds/agent_beats_to_script.sql`), ответ в рамке `===STORY===…===END===` (парсер отрезает всё снаружи).
Сиды данных — `supabase/seeds/*.sql` (идемпотентные).
На каждом переходе человек принимает результат. Стадия серии **вычисляется** по данным (`topicStage` в store): idea → beats → script → shots → frames → published; руками не ведётся. Связи между сериями пишутся в тексте бита: «проклятие (→10)».

## Сценарий

`topics.script_scenas` — результат агента-сценариста (раньше писался в `extended_description`): история, разбитая по локациям и сценам. По нему потом строятся шоты в `scenes`. Парсер: `lib/script.ts`. Формат:
```
=== ЛОКАЦИЯ: <название> ===
@Scene: <N> — <бит>
@Characters: A, B
Описание: <текст; реплики вида «X говорит: «…»»>
——            (разделитель сцен)
```
Сцена сценария сопоставляется с шотами по `scenes.scena = N`. Строки, которые парсер не узнал, показываются как предупреждения. Исходник можно править в боковой панели, таблица перестраивается на лету.

## Раскадровка и генерации

Главная задача админки — раскадровка: кадр (картинка) для каждой сцены.

**Текущий процесс (ручной).** Персонажей генерируют в ComfyUI, кладут в папку ролика и вписывают путь в `characters.base_img`. Затем по каждой сцене:
1. Взять промпт кнопкой «Для ComfyUI»: промпт плюс пути к картинкам персонажей.
2. Дорабатывать промпт, пока картинка не получится.
3. Сработавший промпт записать в `scenes.manual_prompt`, файл положить по схеме и вписать путь в `base_image_url`.

Пары `visual_prompt` → `manual_prompt` потом используем, чтобы улучшить автоматические промпты.
- `visual_prompt` — **авто-промпт, вручную не перезаписываем**; правка человека идёт только в `manual_prompt`. В карточке сцены показывается разница (`PromptDiff`).
- Пути в БД — **относительно ComfyUI/output** (схема в `lib/media.ts`):
  `anima/<seasons.folder>/characters/<slug имени>.png` (персонажи — общие на сезон), `anima/<seasons.folder>/<topics.folder>/<scena 2 знака>-<shot_num>.png` (кадры лежат прямо в папке серии, без `scenes/`). `seasons.folder` назначается так же, как `topics.folder` (`assignSeasonFolders`).
- `topics.folder` — папка ролика: транслит названия, при совпадении `-2`, `-3`… Назначает **админка** (единственное место, где создаются ролики) один раз, как только у ролика есть настоящее название (не «Новый ролик»): `assignFolders` в `store/data.tsx`, `uniqueFolder` в `lib/media.ts`. Дальше не меняется — переименование ролика пути не ломает. В БД — только колонка и уникальный индекс `topics_folder_key` (`supabase/topic_folder.sql`), триггеров нет.
  Полный путь тоже понимается: корень `VITE_MEDIA_ROOT` (по умолчанию = `MEDIA_DIR`) или всё до `/output/` отрезается. `PathHint` под полем подсказывает путь и предлагает сократить полный.
- Класть **оригинальные PNG из ComfyUI** (в них зашиты workflow/промпт/seed) — позже вытащим `manual_prompt` автоматически.
- Статусы сцены как прогресс: draft → ready (кадр есть) → approved.

**Генерация из админки (n8n).**
- Админка ставит `scenes.status = 'generating'` и шлёт POST на вебхук n8n (`VITE_N8N_IMAGE_WEBHOOK`, в dev идёт через прокси `/n8n`, чтобы не было CORS). Тело запроса: `{action:'scene_image', scene_id, topic_id, output_prefix, prompt (= manual_prompt || visual_prompt), visual_style, requested_by, scene, characters}` (`characters` — записи персонажей сцены). Если вебхук ответил ошибкой, статус становится `'error'`.
- n8n запускает ComfyUI с `filename_prefix = output_prefix` (`anima/<сезон>/<серия>/03-1`), затем пишет в БД относительный путь `base_image_url = 'anima/<сезон>/<серия>/03-1_00001_.png'` и `status = 'ready'` (или `'error'`).
- Пока есть сцены в статусе `generating`, админка обновляет данные каждые 4 с.
- Файлы лежат на диске сервера (ComfyUI/output), в Supabase Storage не кладём. Фронт строит URL через `mediaUrl()` (`lib/media.ts`) как `VITE_MEDIA_BASE_URL` + путь; полные http-URL отдаются как есть. В dev папка `MEDIA_DIR` раздаётся плагином в `vite.config.ts` по `/media`, в проде это делает nginx.

## Цель и план (ноябрь 2026)

**Зачем админка сейчас.** Бэкенд (n8n + ComfyUI) работает полностью: на нём сделано 10 роликов (пара — фотореализм, остальные — мультфильмы). Админка — **демонстрация управляемого конвейера** для продажи (ТВ-контент, продавцы-партнёры): весь путь от идеи до ролика по шагам, у каждого шага кнопка, статус и превью результата, любой шот можно поправить и перегенерировать. Это не мультипользовательский продукт.
- **Критерий для любой задачи: видно ли это в 10-минутном показе «от идеи до готового ролика»?** Нет — откладываем. Сейчас не делаем: роли/онбординг/биллинг, обобщение под «любой проект», агент правки данных, раскладку полей для других карточек.
- Демо-цепочка на одной серии: сезон (логлайн, библия, персонажи) → рыба → сценарий → шоты → кадры → озвучка → видео шотов → монтаж → готовый ролик.

**Кнопки озвучки, видео и монтажа** (сделано в админке; ждут вебхуков в n8n).
- Процессы уже есть в n8n и работают на уровне шота: у шота есть всё нужное для видео с озвучкой. n8n сам пишет результат в существующие поля: `scenes.audio_file`, `audio_duration`, `video_file`, `music_file`, `video_sub`, `topics.url_final`. **Админка только запускает вебхук и показывает поля** — данные не собирает, новых таблиц и полей нет.
- Вебхуки (пользователь добавит в n8n). Админка шлёт только id, ответ — сразу 200, дальше асинхронно:
  | Шаг | Переменная | Тело |
  |---|---|---|
  | Озвучка шота | `VITE_N8N_AUDIO_WEBHOOK` | `{ scene_id }` |
  | Видео шота | `VITE_N8N_VIDEO_WEBHOOK` | `{ scene_id }` |
  | Монтаж серии | `VITE_N8N_MONTAGE_WEBHOOK` | `{ topic_id }` |
  | Музыка локации (Suno) | `VITE_N8N_MUSIC_WEBHOOK` | `{ topic_id, location_num, scene_ids }` |
  Нет переменной — кнопка неактивна с подсказкой «вебхук не настроен».
- Карточка шота: кнопки «Озвучить» и «Видео», плееры `audio_file` (с длительностью) и `video_file`.
- Таблица шотов: массовые «Озвучить» / «Видео» по выбранным (как генерация кадров); компактная колонка готовности кадр · аудио · видео — считается по заполненности полей, без новых статусов.
- Страница «Озвучка» (`/voice/<серия>`, `pages/Voice.tsx`): сцены серии с непустым `dialogue_text` — кто говорит, голос, реплика, подача, плеер `audio_file`, длительность аудио, «Сек»; кнопка в строке, «Озвучить выбранные», «Озвучить неозвученное» (все реплики без `audio_file`). Клик по строке — обычная карточка сцены.
- Страница «Анимация» (`/animation/<серия>`, `pages/Animation.tsx`): как «Раскадровка», но в плитке видео шота (`video_file`, играет без звука при наведении; нет видео — кадр полупрозрачно) и под ним видео-промпт из `scenes.action`. Фильтр «Без видео». Клик — карточка сцены.
- Страница «Музыка» (`/music/<серия>`, `pages/Music.tsx`): шоты серии по локациям (`location_num`, без номера — `location_desc`). У локации — её шоты, сумма длительностей (длина трека), описание для Suno (`scenes.music`, сохраняется во все шоты локации), плеер `music_file`, кнопка «Сгенерировать музыку» → `VITE_N8N_MUSIC_WEBHOOK`, тело `{action:'location_music', topic_id, location_num, scene_ids}`; n8n генерирует в Suno и пишет `music_file` во все `scene_ids`. Запуск отслеживается по первому шоту локации (`runMusic`).
- Страница «Монтаж» (`/montage/<серия>`, `pages/Montage.tsx`): экран сверху, таймлайн снизу (линейка · видео · голос · музыка). Склейка встык, порядок — `scena`/`shot_num`, без подрезки и перетаскивания. Длительность шота = `audio_duration || time || 3`. «Черновик» проигрывает `video_file` подряд в браузере (шот без видео — кадром на свою длительность), метка проигрывания по центру, лента едет; «Готовый ролик» — `url_final`. Музыка на таймлайне — блоки подряд идущих шотов с одной `music`/`music_file`, иначе по локации. Кнопка «Смонтировать» (подтверждение, если не у всех шотов есть видео). **Переходы** (ffmpeg `xfade`) — позже: поле у сцены + поддержка в монтаже n8n.
- Карточка серии: кнопка «Смонтировать»; плеер `url_final` уже есть.
- Шоты — это строки `scenes` (страница «Сцены»), отдельной таблицы нет. Колонка «Готово» в таблице сцен: три точки кадр · аудио · видео.
- Статуса в БД у этих запусков нет: админка держит их в памяти вкладки (`runJobs` / `isRunning` в `store/data.tsx`). Запуск снимается, когда у строки изменились поля результата или `updated_at` (`jobSig`); через 20 мин — с предупреждением. Пока есть запуски, данные обновляются каждые 4 с. Перезагрузка вкладки индикатор теряет — результат всё равно придёт в поля.
- Музыка (по локации) накладывается **при монтаже** — отдельной кнопки нет.
- Длительность видео шота: есть `audio_file` — по аудио, нет — по `scenes.time` (колонка «Сек»). В карточке без озвучки пишем, по какому времени пойдёт видео; если нет ни аудио, ни `time` — подтверждение перед запуском (в карточке и при массовом запуске).

**Вычисления** (`/compute`, `pages/Compute.tsx`, `api/compute.ts`, `server/comfy.ts`). Плитки: серверов онлайн, генераций сегодня, время GPU сегодня, всего генераций.
- **Свои серверы** — из `COMPUTE_SERVERS` в `.env.local`: `название|адрес ComfyUI|для чего|$ в час`, несколько через `;` (без переменной — `VITE_COMFY_URL`). Сейчас: локальный RTX 2080 Ti 11 GB (`192.168.1.99:8188`, фото); позже Таиланд 24 GB, потом RunPod. Карточка: статус (свободен / генерирует · очередь / нет связи), GPU, видеопамять и ОЗУ, статистика (сегодня, фото/видео со средним временем, всего, время GPU, ошибки, себестоимость при цене > 0), последние 15 генераций. Данные — прямо из ComfyUI (`/system_stats`, `/queue`, `/history`) через сервер админки, без проверки входа (только чтение; ComfyUI и так открыт в локальной сети). Тип генерации — по расширению результата. **История ComfyUI в памяти — после его перезапуска статистика с нуля**; постоянная статистика и себестоимость серии — позже, журналом генераций из n8n.
- Сервер без адреса (`Таиланд 24 GB||видео|0`) — карточка «Не настроен».
- **RunPod — такая же карточка** (`RunPodCard`): статус (нет подов / работает…), GPU и дата-центр, баланс, цена, сессия; у работающего пода — статистика его ComfyUI через прокси RunPod. `GET /compute/pods` — без проверки входа (только чтение: проверка входа через Supabase с сервера админки нестабильна, «Нужно войти в админку»); `POST /compute/pods/:id/start|stop` — с проверкой, в интерфейсе пока не выведены (`RunPodSection` с карточками подов не рендерится). Ключ `RUNPOD_API_KEY` в `.env.local` без `VITE_`. Под с сетевым томом нельзя остановить — только удалить; создание подов — позже, нужен свой Docker-образ.
- Серверная часть — плагин `runpodApi` в `vite.config.ts` (процесс dev/preview-сервера, как `/media`) + `server/comfy.ts`. Проект `/Users/pele/Dev/runpod` админке не нужен.

## Решения по ТЗ (согласовано с заказчиком)

- **Только быстрая карточка справа**, без нижней «расширенной». Клик по строке открывает карточку, чекбокс — для массовых действий.
- **Контекстная панель ролика** — только на странице «Сцены».
- **Оплаты нет.** Задач генерации (Task) **нет** — в БД такой таблицы нет; вернёмся, когда появится.
- **Агенты — реальная таблица `agents`** (промпт + модель). **Настройки — демо** (in-memory, `src/api/demo.ts`, бейдж «демо» в меню): таблиц нет. API-ключи write-only (наружу только `key_hint`).
- **Перетаскивание сцен отключено**: порядок задаётся полями `scena`/`shot_num`, правится в карточке.
- **Резиновая вёрстка**, карточка на `xl+` раздвигает контент, на узких — оверлей.
- Интерфейс только на русском; комментарии/история/уведомления — отложены.

## Архитектура

```
src/
  types.ts            — Topic, Scene (= колонки БД) + демо-сущности
  lib/supabase.ts     — клиент Supabase (anon key)
  api/types.ts        — интерфейс Api (контракт слоя данных)
  api/supabase.ts     — topics/scenes/characters/agents через Supabase (постраничная выборка по 1000)
```

### Принципы

- UI ходит в данные только через `api`. Новая таблица → методы в `Api` + реализация в `api/supabase.ts`.
- Пустые значения nullable-полей сохраняются как `null` (не `''`); NOT NULL поля помечаются `required` в FieldDef.
- Маршруты: `/seasons/:seasonId?` (`?ep=<topic_id>`), `/dashboard`, `/topics/:topicId?`, `/scenes/:topicId?` (`?scene=<id>`), `/script/:topicId?`, `/storyboard/:topicId?` (`?scene=<id>`), `/characters/:seasonId?` (`?character=<id>`), `/agents` (`?agent=`), `/settings/:section?`. Выбранная сущность — в URL.
- Настройки таблиц и фильтры — в localStorage по `storageKey`.
- Эталон вида владельца — `ui-settings.json` в корне проекта (скачивается в «Настройки → Интерфейс», `lib/uiSettings.ts`). При старте применяется, если `exported_at` новее применённого: ключи столбцов/раскладки карточек перезаписываются, остальное (фильтры, выбор сезона/ролика) не трогается.
- Карточки описываются через `GroupDef/FieldDef`; новое поле БД = строка в конфиге группы.
- Права проверяет БД (RLS); фронт ничего не скрывает «для безопасности».
- **Всё, что создаём в БД (таблицы, колонки, функции, триггеры, политики), лежит в `supabase/*.sql`.** Каждый объект подписан через `comment on … is '… Источник: anima_admin/supabase/<файл>.sql'`. Скрипты идемпотентные. Логику держим в коде админки; триггеры — только если в таблицу пишут несколько участников и иначе не обойтись (сейчас триггеров нет).
